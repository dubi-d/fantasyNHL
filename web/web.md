# web

The browser front end: a React/TypeScript single-page app that renders
the views served by the [api](../src/fantasy_nhl/api/api.md). It has one
page per tool, with the terminal's prompts as form controls.

## Boundaries

- Talks to the backend over `/api` only; it holds no fantasy logic and
  formats nothing. Tables arrive as text plus tones, figures as images.
- The types of everything it receives are generated from the backend's
  schema, never written by hand.

## Commands

Run in `web/`; Node.js 20.19+ or 22.12+.

```bash
npm ci           # install exactly what package-lock.json says
npm run build    # typecheck, then build into dist/ (served by the backend)
npm run dev      # hot-reloading dev server on http://127.0.0.1:5173
npm test         # unit and component tests (vitest)
npm run types    # regenerate src/schema.d.ts from openapi.json
```

The dev server proxies `/api` to the backend on `127.0.0.1:8000`
([vite.config.ts](vite.config.ts)), so start one next to it:

```bash
.venv/bin/fantasy-nhl-web                        # your leagues, or
.venv/bin/python tests/fake_server.py [scenario] # the synthetic league, no ESPN
```

## Key concepts

- **The address is the state.** `#/<league>/<page>?<choices>`: the league
  is the first part of the path, and a page keeps every choice in the
  query through `usePageParams` (`get`, `list`, `set`). Reload, back and
  forward and bookmarks therefore work. What decides which view is shown
  is never held in `useState`.
- **Defaults are not stored.** A choice the user has not made is absent
  from the address and computed from the league's current state (current
  matchup, latest completed matchup), so it follows the league after a
  reload. Values taken from the address are clamped to what is valid.
- **Remembered outside the address:** the tab's last league
  (`sessionStorage`, so a new tab starts on the default league), the stats
  setting and the planner's team per league (`localStorage`).
- **Views are queries.** `useView(path, params)` fetches a view; its
  address is the query key. While another choice loads, the previous view
  stays on screen, dimmed.
- **Never build controls from a stand-in view.** While the previous view
  stands in, its `meta` belongs to other choices. Use `currentMeta(query)`,
  which is empty in that case; the planner additionally keeps the meta of
  the same team and week while only the streamers change.
- **One renderer.** `ViewPanel` renders any view: tables with tones,
  notes, copyable text, figures. A page adds only its form.
- **Freshness.** A view is asked for again once it is five minutes old
  (on returning to the page or the window). *Reload from ESPN* tells the
  backend to drop the league and refetches everything shown.

## Extending

1. Add the endpoint and regenerate `openapi.json` and `src/schema.d.ts`
   (see [api.md](../src/fantasy_nhl/api/api.md)).
2. Write the page in `src/pages/`: choices from `usePageParams`, the view
   from `useView` or `RemoteView`, controls from `controls.tsx`.
3. Add it to `MENU` in `App.tsx`.
4. Add a component test for anything beyond a plain view.

## Gotchas

- A `Field` is a `<label>`: put exactly one control in it. Several
  controls under one caption (checkboxes, chips) go in a `Group`,
  otherwise a click on the caption hits the first control.
- TypeScript is pinned to version 5: the type generator
  (`openapi-typescript` 7) does not run on TypeScript 7.
- `dist/` is not committed. The backend warns when it is missing or older
  than `src/`.
- A hash change does not reload the app: after rebuilding, reload the
  browser tab to get the new bundle.

## Tests

- `app.test.tsx` renders the whole app in jsdom against scripted server
  answers (`serve({address: json})`): the default league, addresses,
  the planner's stand-in rule, reload, error states.
- `schema.test.ts` fails when `schema.d.ts` no longer matches
  `openapi.json`.
- `tone.test.ts` pins the gradient to the terminal's.

See [tests.md](../tests/tests.md) for the backend side.
